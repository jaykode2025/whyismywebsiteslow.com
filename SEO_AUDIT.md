## 3. Broken / conflicting technical SEO

- **Two conflicting `robots.txt` sources.** `public/robots.txt` (static, `Allow: /` with no disallows, non-www sitemap URL) vs. `src/pages/robots.txt.ts` (dynamic, correctly disallows `/api/` and `/r/`, correct www sitemap URL). The static file was winning the build. **Fixed this session** - deleted the static file.
- **`/api/debug` had zero auth** - crawlable-if-linked, and directly reachable regardless of robots.txt. **Fixed this session** (see `PROJECT_AUDIT.md` §10).
- **Pre-existing bug in `sitemap.xml.ts`**: `getCollection("pages")` entries were referenced as `page.slug`, a field that does not exist on legacy content-collection entries in this Astro version (only `.id` does, and it includes the file extension). This was silently masked because the collection was always empty before this session's fix - the moment it started returning real entries, every guide URL in the sitemap would have been `undefined`. **Fixed this session.**
- **JSON-LD `logo` 404 and fabricated `contactPoint` phone number** (`src/lib/seo.ts`, emitted via `organizationSchema()`/`articleSchema()` on most pSEO pages and now on guides). **Fixed this session** - logo now points at the real `/og-default.png`; the fake phone number was removed rather than fixed with another fake value.
- **Canonical host mismatch**: `astro.config.mjs`'s `site` and `src/lib/seo.ts`'s `siteUrl()` both use `www.whyismywebsiteslow.com`; the (now-deleted) static `robots.txt` used the non-www apex. No longer an issue after the robots.txt fix, but worth noting the pattern - grep for hardcoded non-www URLs if adding new pages.
- **Sitemap redundancy**: `@astrojs/sitemap` integration auto-generates `sitemap-index.xml`/`sitemap-0.xml` (crawls static routes only, so it won't include reports or the dynamic guide/pSEO routes correctly) *alongside* the hand-written `src/pages/sitemap.xml.ts` (which does include everything). Both exist and both are referenced from different places. **Recommend** (not done this session, low risk either way): pick one. If keeping both, at minimum make sure the canonical `Sitemap:` line in `robots.txt.ts` always points at the complete one (`/sitemap.xml`), which it does.

## 4. Keyword cannibalization

### Real, direct cannibalization (needs a decision, not fixed here)

**`too-many-plugins-making-wordpress-slow` (guide)** vs. **`why-is-my-wordpress-site-slow-issue-1`** (`src/data/pseo.ts`, `keyword: "why is my wordpress site slow too many plugins causing"`, `issueTitle: "Too many plugins causing bloat"`) vs. **`why-is-my-wordpress-site-slow-plugin-bloat`** (a third, more specific templated page). All three target essentially the same query intent ("too many WordPress plugins slowing my site"). The hand-written guide is meaningfully better content (specific, has a real recommendation with disclosed affiliate context, no templated filler); the `-issue-1` page is thin, auto-generated, near-identical in structure to 79 other "issue-N" pages (see below).

**Recommendation:** treat the guide as the canonical target for this keyword (it now outranks in internal link weight - it's linked from the WordPress platform hub, the guides index, and sibling guides). Do **not** delete the pSEO pages yet (that's a bigger call requiring traffic data you don't have yet), but do not build any more content targeting this exact phrase. If/when you have Search Console data, `noindex` whichever of the two pSEO variants is getting zero impressions.

### Structural cannibalization risk (the "issue-N" pages)

Of the 150 unique problem-page slugs, **80** (10 platforms × 8 each) follow the pattern `why-is-my-{platform}-site-slow-issue-{1-8}`. Inspecting the actual data (`why-is-my-wordpress-site-slow-issue-1` vs. `-issue-2` etc.) shows:
- Identical `statistics` block on every single one: `40%` / `2.3s` / `15%` - not platform- or issue-specific, just filler.
- Identical sentence templates (`"{platform} sites often experience performance issues due to {issue}."`, `"Diagnose the exact cause of {issue}"`, etc.) with only the noun phrase substituted.
- Identical `outboundLinks` (same 3 URLs: WordPress.com performance docs, Google PSI, web.dev vitals) regardless of platform.

This is the textbook shape of content that underperforms under Google's Helpful Content system: real information density is near-zero, and 80 pages share the same skeleton. The **5 named-issue pages per platform** (e.g. `wordpress-site-slow-plugin-bloat`, `-render-blocking-assets`, `-slow-ttfb`) and the platform/industry/location hub pages are qualitatively different - populated with real per-platform issue lists (`topIssues`, `commonSolutions` from `PLATFORMS`), not filler.

**Recommendation (not implemented - a data/traffic decision, not a code fix):** once there's Search Console data, `noindex` the "issue-N" pages that get zero clicks/impressions rather than deleting them outright (they may still serve as internal-linking scaffolding). Do not generate more pages in this pattern.

### Data bug found while verifying counts: duplicated, mis-keyworded `INDUSTRIES`/`PLATFORMS` entries

`INDUSTRIES` in `src/data/pseo.ts` has **15 array entries for 9 unique industries** - `healthcare`, `finance`, `education`, `real-estate`, `travel`, and `restaurant` each appear **twice**, and all 6 duplicates carry the wrong `keyword` field: `"website speed audit for ecommerce"` (copy-paste leftover from the ecommerce template), instead of their real keyword (e.g. finance's duplicate says "for ecommerce" instead of "for financial services"). `PLATFORMS` has the same shape (16 entries for 10 unique platforms: `magento`, `react`, `vue`, `angular`, `nextjs`, `gatsby` each duplicated), though spot-checking those duplicates didn't turn up a mismatched `keyword` field the way `INDUSTRIES` did.

**Practical impact:** `staticPaths.ts`'s `generateIndustryPaths`/`generatePlatformPaths` naively `.map()` the full array (including duplicates) into static paths, so Astro generates the same output URL (e.g. `/website-speed-audit/industry/finance/`) from two different array entries. Because every page component resolves its data via `.find()` (which returns the *first* array match), the **live page content is unaffected** - it always resolves to the correct first entry. This is wasted build work and confusing dead data, not a visible bug on the site today. **Recommended fix (not done this session - a data file edit outside the scope of the P0/P1 list):** delete the 6 duplicate entries from each array in `src/data/pseo.ts`.

### Second pSEO system overlap

The root-level `[slug].astro` (driven by `performance-datasets.json`, currently only 2 entries) covers WordPress-mobile-slowness topics that also exist inside `pseo.ts`'s 150 problems and now in the `/guides/` article set. With only 2 live entries this is a small risk today, but it's a third rendering path/component set (`ReportProofBlock.astro`) for the same subject matter. **Recommend**: don't expand this dataset further; fold anything planned for it into either `pseo.ts` or `/guides/` instead.

## 5. Metadata quality

- **Titles/descriptions**: verified per-page-unique across `BaseLayout.astro` consumers (index, scan, report, fix/*, why-is-my-website-slow/*, website-speed-audit/*, about-seo-engine, and now guides). Not generic/duplicated - this part of the SEO implementation is solid.
- **Canonical URLs**: correctly computed per page (`BaseLayout.astro`'s fallback to `Astro.site?.origin + Astro.url.pathname`, or an explicit `canonical` prop where needed, as on guides).
- **Structured data**: rich and mostly correct (BreadcrumbList, FAQPage, Article, Dataset on report/problem pages) - the two real defects (404 logo, fake phone number) are fixed this session.
- **OG images**: dynamic per-page-type OG image generation exists (`src/pages/og/**`) - a genuinely above-average feature for a project this size.

## 6. Content gaps (see `CONTENT_CLUSTER_PLAN.md` for the prioritized roadmap)

- **Core Web Vitals** has no dedicated hub page. `/fix/lcp`, `/fix/ttfb`, `/fix/render-blocking-css` exist as isolated fix pages with no CWV overview/hub linking them together, despite CWV being one of the highest-intent short-tail clusters (see `SEO_KEYWORD_MAP.md` Cluster B).
- **Squarespace and WooCommerce** have zero programmatic (pseo.ts) coverage - they're only covered by 1 guide article each. Real gap given both are large, distinct platforms with different performance failure modes than WordPress/Shopify.
- **Image optimization, font loading, third-party scripts** clusters (Cluster F in the keyword map) have no dedicated pages at all - only passing mentions inside problem-page bodies.
